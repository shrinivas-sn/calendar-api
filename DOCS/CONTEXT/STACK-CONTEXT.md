## Backend — terminal error handler (FIXED 2026-08-16)

> **Status: resolved.** `backend/src/index.js` now carries a 4-arg terminal handler,
> registered last. Keep the rest of this section — it is the reasoning that stops the
> handler being deleted or moved by someone who does not know why the arity matters.

The file used to end with only a **2-argument** wildcard handler:

```js
app.use((req, res) => {
  sendError(res, "Endpoint not found", 404);
});
```

Express decides "request handler vs error handler" purely by arity — 4 args or it is not an
error handler. So this catches unmatched *routes* and never sees an error. With no 4-arg
handler anywhere in the file, any error escaping a route's local `try/catch` fell through
to Express's built-in `finalhandler`.

Every `/v1` route wraps its body in `try/catch` (lines 145, 175, 226, 290, 354), which is why
it never showed up in normal use. Those blocks do not cover middleware: `express.json()` at
line 29 throws on a malformed body, and that error bypasses every `catch` in the file.

**Observed before the fix** (reproduced on a matching `express@5.2.1` stack):

- `NODE_ENV` unset → `400 text/html` with a `SyntaxError` stack trace and absolute server paths.
- `NODE_ENV=production` → `400 text/html`, body `Bad Request`.

So production env only removed the stack trace. **Either way the response was HTML**, which
broke the documented `{error, message, status}` JSON contract — a client calling
`res.json()` got a parse failure instead of a readable error.

### The fix now in the file

Sits after the 404 handler, immediately before `app.listen`:

```js
app.use((err, req, res, next) => {
  const status = err.status || err.statusCode || 500;
  if (status >= 500) console.error(err);
  sendError(res, status >= 500 ? "Internal Server Error" : err.message, status);
});
```

It reuses the existing `sendError` helper, so every error path returns the same envelope the
rest of the API already uses.

**Two rules for anyone editing that end-of-file block:**

- `next` is unused *on purpose*. It is the fourth argument, and the fourth argument is the
  only thing making this an error handler. A linter flagging it as unused is wrong here —
  silence the linter, do not drop the parameter.
- It must stay **last**. Registering any `app.use` after it means errors reach `finalhandler`
  again and the HTML regression is back.

Note that Express 5 auto-catches rejected promises from `async` handlers — the existing
`try/catch` blocks are no longer required for that, though they are harmless. Do **not**
add `express-async-handler`; it is a v4-era workaround.

## Frontend — the slate scale is remapped, and it is Tailwind v3

`tailwind.config.js` restates all 11 `slate` shades under `theme.extend.colors`. Only two
actually differ from stock `tailwindcss@3.4.19`:

| Class | Stock | Here | Effect |
|---|---|---|---|
| `slate-400` | `#94a3b8` | `#e2e8f0` | renders as stock **slate-200** |
| `slate-500` | `#64748b` | `#cbd5e1` | renders as stock **slate-300** |

The other nine match the defaults exactly and are noise. The comments in the config say the
intent was a deliberate contrast bump for the dark theme — this is a real decision, not a
bug, and there are **121 usages** of `slate-400`/`slate-500` across `src/` depending on it.

**What this means when writing new UI here:** the habitual "muted secondary text →
`text-slate-400`" produces *near-white* text in this project. For genuinely muted text on
the `slate-900` background, reach for `slate-600`, or add a named token rather than
deepening the reliance on a remapped built-in.

### Version rules

- This is Tailwind **v3**: `@tailwind base/components/utilities` in `src/index.css`, JS
  config, `postcss.config.js` + `autoprefixer`, and the `theme()` function used in
  `index.css`. Do **not** introduce v4 syntax (`@import "tailwindcss"`, `@theme`,
  `@tailwindcss/vite`) — it fails silently, emitting no utilities rather than erroring.
- There are **zero** `dark:` variants in `src/` and no `darkMode` key in the config. The
  dark look is baked into base styles, so adding `dark:` classes here does nothing.
- The frontend is plain **JS/JSX**, not TypeScript, despite `@types/react` being installed.

## Frontend — motion and focus conventions (ESTABLISHED 2026-08-16)

> **Status: resolved.** This section is a convention to hold to, not open work.

The original defect was logged as *one* `transition-all` in `index.css`. Rescanning with the
full `slop-signatures.md` sweep found the record understated its own scope by ~10×:

| Found | Count |
|---|---|
| `transition-all` | **20**, across 8 files |
| Buttons with any focus state | **0 of 14** |
| `prefers-reduced-motion` blocks | **0** |

All three are now closed. The conventions that came out of it:

- **No `transition-all`.** Name the properties: `transition-[transform,box-shadow]`,
  `transition-[background-color,border-color]`, and so on. `transition-all` animates layout
  and paint properties too, forcing paint on every hover frame. Current count in `src/` is
  **0** — keep it there.
- **Focus lives on the base `button` rule** in `index.css`, not per component. That is why
  grepping `focus-visible` returns 2 hits rather than 14 — one rule covers every button.
  Adding a new button needs no focus classes; overriding `outline`/`ring` on one will
  silently opt it out.
- **`focus-visible`, not `focus`** — keyboard users get the ring, mouse users do not.
- **A global reduced-motion floor** sits last in `index.css`. It is global rather than
  per-component because nothing this app animates (hover lift, button scale, the glow
  circles) carries meaning. Treat it as an accessibility requirement, not polish.

Verified by `npm run build`: both the reduced-motion block and the focus-visible ring are
present in the emitted CSS, so the arbitrary-value classes are compiling, not being dropped.
